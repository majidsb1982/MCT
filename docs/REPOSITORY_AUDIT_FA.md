# گزارش بررسی و سامان‌دهی مخازن GitHub

تاریخ بررسی: 2026-10-16  
وضعیت: بررسی اولیه مستند شده؛ پاک‌سازی مخرب عمداً انجام نشده است.

## خلاصه تصمیم

- **مخزن انتشار فعلی:** `MCT` را فعلاً حفظ می‌کنیم؛ صفحه زنده آن `https://majidsb1982.github.io/MCT/` است.
- **منبع اصلی پیشنهادی برای بررسی قابلیت‌ها:** `My-Class-Track`، چون README آن دقیقاً نیازهای کلاس گروه‌درمانی را شرح می‌دهد و CI و ابزارهای بررسی پروژه را معرفی می‌کند.
- **منبع قابلیت‌های تکمیلی:** `Mctgem`؛ معماری آن React/TypeScript/Vite است و با MCT ساده JavaScript متفاوت است، پس ادغام فایل‌به‌فایل امن نیست.
- **نامزدهای هم‌پوشان:** `Mctgem-v13`، `class-tracker-pro` و `group-therapy-management`.
- **پروژه‌های جدا:** `forklift-spare-parts-system` و `mlmvpn-cloud-tunnel` نباید با خانواده مدیریت کلاس ادغام شوند.
- هیچ مخزنی حذف نشده و شاخه اصلی/صفحه زنده MCT تغییر نکرده است.

## تفاوت مهم میان «هم‌پوشانی» و «تکراری بودن»

اشتراک امکاناتی مانند حضور و غیاب یا تقویم شمسی، به‌تنهایی اثبات نمی‌کند که دو مخزن نسخه‌های یکسان‌اند. MCT از فایل‌های JavaScript ساده استفاده می‌کند، در حالی که Mctgem بر پایه React/TypeScript/Vite است و class-tracker-pro طبق README ساختار IndexedDB دارد. بنابراین ادغام امن باید **انتقال قابلیت هدفمند** باشد، نه ادغام کورکورانه فایل‌ها یا پوشه‌ها.

## ریسک‌های مهم پیش از هر پاک‌سازی

1. داده‌های برنامه در مرورگر ممکن است به origin، کلیدهای ذخیره‌سازی و نسخه ساختار داده وابسته باشند؛ تغییر آدرس انتشار می‌تواند دسترسی به اطلاعات قبلی را مختل کند.
2. در MCT ترتیب بارگذاری چهار فایل JavaScript مهم است. تغییر ترتیب می‌تواند توابع را پیش از تعریف‌شدن فراخوانی کند.
3. Service Worker و کش آفلاین باید پس از هر انتشار تست شوند؛ تغییر نام فایل‌ها بدون نسخه‌گذاری درست می‌تواند نسخه قدیمی را نگه دارد.
4. در Mctgem، `index.html` دارای کد پاک‌سازی مرتبط با Service Worker/cache است؛ رفتار آن باید جداگانه بررسی شود تا باعث حذف غیرمنتظره کش‌های برنامه نشود.
5. گزارش‌های گروه درمانی ممکن است حاوی داده حساس باشند؛ هیچ داده واقعی اعضا نباید وارد README، issue عمومی یا گزارش audit شود.
6. README و توضیحات قابلیت‌ها جایگزین بررسی کامل کد، hash فایل‌ها و اجرای تست نیستند.

## برنامه اجرایی پاک‌سازی

### مرحله ۱ — تثبیت نسخه امن
- نگه‌داشتن `MCT` به‌عنوان مقصد انتشار فعلی.
- نگه‌داشتن PR گزارش در شاخه جداگانه؛ هنوز لازم نیست آن را با main ادغام کنیم.
- تهیه نسخه پشتیبان از داده‌های داخل برنامه با قابلیت خروجی JSON، در صورت وجود داده واقعی.

### مرحله ۲ — انتخاب نسخه مرجع
- اجرای بررسی‌های معرفی‌شده در README مخزن `My-Class-Track`: `node tools/check-project.mjs` و `node tools/check-html.mjs`.
- اجرای `node tools/smoke.mjs` در محیط دارای Chrome.
- اجرای `npm run build` و تست‌های `class-tracker-pro` و `Mctgem` در محیط توسعه.
- مقایسه کد ذخیره‌سازی، مهاجرت داده، تقویم شمسی، گزارش‌های حامی، دسترسی نقش‌ها و رفتار آفلاین.

### مرحله ۳ — انتقال کنترل‌شده
- قابلیت‌های مفید و غایب را در شاخه مهاجرت جداگانه اضافه کنیم.
- برای داده‌های قدیمی، مهاجرت سازگار و مسیر بازگشت تعریف کنیم.
- روی موبایل و دسکتاپ، حالت آنلاین/آفلاین، تم روشن/تیره، نصب PWA، یادآورها و خروجی/بازیابی را تست کنیم.
- فقط پس از قبولی تست‌ها، تغییرات را به مقصد انتشار منتقل کنیم.

### مرحله ۴ — آرشیو و حذف
- نسخه‌های قدیمی ابتدا Archive شوند، نه اینکه فوراً حذف شوند.
- حذف نهایی فقط پس از تأیید نبودن وابستگی، حفظ تاریخچه لازم و اطمینان از پشتیبان انجام شود.
- ابزار متصل فعلی امکان مقایسه کامل درخت همه مخازن و حذف امن کل مخزن را در این مرحله فراهم نکرده است؛ به همین دلیل هیچ حذف خودکاری انجام نشده است.

## نتیجه

این ممیزی اکنون بر پایه فایل‌های واقعی `index.html`، `js/app.js`، READMEها و `package.json` دقیق‌تر شده است؛ بااین‌حال، هنوز ادغام واقعی کد یا تست اجرایی کامل انجام نشده است. تصمیم فعلی: حفظ نسخه زنده، بررسی عمیق‌تر `My-Class-Track` و `Mctgem`، و خودداری از حذف مخازن تا وقتی برابری کد و نبود وابستگی اثبات شود.
